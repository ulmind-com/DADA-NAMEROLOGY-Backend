# Deploying to Render

Two services: the **API** (this repo) and the **admin panel**
([DADA-NAMEROLOGY-Admin](https://github.com/ulmind-com/DADA-NAMEROLOGY-Admin)).
The mobile app is not hosted — it ships through EAS to the app stores.

Deploy the API first: the admin panel needs its URL at build time.

---

## 1 · API

Both repos contain a `render.yaml`, so Render can set the service up for you.

**Render → New → Blueprint → connect `DADA-NAMEROLOGY-Backend` → Apply.**

Render reads the blueprint and asks for the values marked `sync: false`. Paste them
from the list you were given:

| Key | What it is |
| --- | --- |
| `MONGODB_URI` | The Atlas connection string |
| `RESEND_API_KEY` | Resend API key (`re_…`) |
| `RESEND_FROM` | `DADA'S NUMEROLOGY <noreply@yourdomain>` — the domain must be verified in Resend |
| `CLOUDINARY_CLOUD_NAME` / `_API_KEY` / `_SECRET` | Cloudinary credentials |
| `GOOGLE_CLIENT_IDS_RAW` | Comma-separated OAuth client ids — leave blank until they exist |
| `CORS_ORIGINS_RAW` | The admin panel's URL. Put `*` for now and tighten it in step 3 |
| `ADMIN_EMAIL` / `ADMIN_PASSWORD` | The super-admin seeded on first boot |

`SECRET_KEY` is generated by Render itself and never leaves the dashboard.
`ENV`, `DEBUG` and `OTP_DEV_ECHO` are already pinned to their production values.

Prefer clicking through by hand? The blueprint is equivalent to:

- **Runtime** Python 3 · **Build** `pip install --upgrade pip && pip install -r requirements.txt`
- **Start** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`

Stay on one worker while on the free plan — 512 MB does not fit two.
- **Health check path** `/api/v1/health`

### Check it came up

```bash
curl https://<your-api>.onrender.com/api/v1/health
# {"status":"ok","env":"production","app":"DADA'S NUMEROLOGY","database":"up"}
```

`"database":"up"` means Atlas is reachable. If it says `down`, fix Network Access
(step 4) before going further.

## 2 · Admin panel

The admin repo carries both a `vercel.json` and a `render.yaml`, so it deploys to either.

### Vercel

**Add New → Project → import `DADA-NAMEROLOGY-Admin`.** Vercel reads `vercel.json` and
detects Vite, so the only thing to set is one environment variable:

| Key | Value |
| --- | --- |
| `VITE_API_URL` | `https://<your-api>.onrender.com/api/v1` |

Add it for **Production, Preview and Development**, then Deploy.

### Render

**New → Blueprint → connect the repo → Apply**, and set the same `VITE_API_URL`.
It builds with `npm ci && npm run build` and publishes `dist`.

### Either way

`VITE_API_URL` is compiled into the bundle, so changing it later needs a fresh deploy
(Vercel: **Redeploy**; Render: **Manual Deploy → Clear build cache & deploy**).

Sign in with the `ADMIN_EMAIL` / `ADMIN_PASSWORD` from step 1.

## 3 · CORS

The default is `CORS_ORIGINS_RAW=*`, which lets the admin panel, Expo web previews and
anything else call the API from a browser.

That is a reasonable default here because authentication is **bearer-token only**. A
hostile page can send a request, but it has no way to attach someone else's token —
tokens live in the admin panel's own storage, which the browser will not share
cross-origin. There are no cookies to ride, so there is no CSRF surface.

If sessions ever move to cookies, narrow it immediately to the exact origin — scheme
and host, no trailing slash, no path:

```
CORS_ORIGINS_RAW=https://your-admin.vercel.app
```

Preview deployments get a new hostname each time, so match those by pattern rather than
listing them:

```
CORS_ORIGIN_REGEX=^https://your-admin(-[a-z0-9-]+)?\.vercel\.app$
```

## 4 · MongoDB Atlas

**Network Access** — Render's free and starter plans use a shared, changing pool of
outbound IPs, so an allowlist cannot be pinned to one address. Either:

- allow `0.0.0.0/0` and rely on the database user's password and role, or
- move to a paid Render plan with static outbound IPs and allowlist those.

**Database user** — give it `readWrite` on `dada_numerology` only, not `atlasAdmin`.

**Backups** — the free M0 tier has no automated backups. If this data matters, an M10
or a scheduled `mongodump` is worth the money.

## 5 · Mobile app

`eas.json` points the production profile at the API. Change the URL there to your real
one, then:

```bash
npm install -g eas-cli
eas login
eas init                       # writes extra.eas.projectId into app.json
eas build --platform android --profile preview      # installable APK for testing
eas build --platform all --profile production       # store builds
eas submit --platform android
```

The API base URL comes from `EXPO_PUBLIC_API_URL`, which EAS inlines at build time.

## Things worth knowing

**Free instances sleep.** After 15 minutes idle, Render's free tier spins the API down;
the next request takes roughly 50 seconds while it wakes. Fine for testing, not for real
users — the Starter plan removes it. A cron ping is a workaround, not a fix.

**Email must work before launch.** With `OTP_DEV_ECHO=false` and no working transport,
signup returns **503** rather than stranding people on a code screen they can never
pass. That is deliberate — but it means Resend has to be configured and its sending
domain verified, or nobody can register.

**PDF sharing works already.** Cloudinary blocks PDF delivery on new accounts, so share
links point at `GET /api/v1/public/reports/{id}?t=…` on the API. To hand out Cloudinary
CDN links instead, enable **Settings → Security → PDF and ZIP files delivery** in the
Cloudinary console — the API notices and switches over on its own.

**`ADMIN_PASSWORD` only applies on first boot.** The seed never overwrites an existing
account's password — otherwise every deploy would undo a password change. If the admin
already exists with a different password, the startup log says so; change it from the
admin panel, or delete the account and redeploy to have it re-seeded.

**Keep dev and production apart.** Set `MONGODB_DB=dada_numerology_dev` locally so
development never writes into the production database on the same cluster.

**Rotate what has been shared.** Any credential that has passed through chat, email or a
ticket should be rotated once you are live: the Atlas password, the Resend key and the
Cloudinary secret.

## Redeploying

Both services have `autoDeploy: true`, so pushing to `main` ships. Roll back from
**Events → Rollback** in the Render dashboard.

After changing a dependency, regenerate the lockfile export the build uses:

```bash
uv export --no-dev --no-emit-project --format requirements-txt > requirements.txt
```
